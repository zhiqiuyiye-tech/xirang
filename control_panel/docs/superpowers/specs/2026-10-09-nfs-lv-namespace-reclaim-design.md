# NFS 逻辑卷残留挂载的安全自动回收

日期：2026-10-09

状态：用户已确认详细设计、默认值及风险，授权代码实现；随后明确要求完成验证后更新版本号并提交推送。独立设计复核已完成，复核修正纳入下文。线上操作和部署仍不在授权范围。

## 1. 理解摘要

- 修复 control_panel 回收 NFS 逻辑卷时，业务 Pod 销毁后 Promtail 容器挂载命名空间残留挂载导致 `lvremove` 报 `contains a filesystem in use` 的问题。
- 用户已完成根因排查；本次以报告为依据，不重复线上调查。
- 面向执行存储回收的管理员；回收成功意味着逻辑卷实际删除成功，空间归还卷组。
- 推荐沿用首次 `lvremove` 报占用后进行受限清理、验证、重试一次的流程。
- 仅在安全条件得到核实后允许自动进入目标挂载命名空间执行普通卸载。
- 活跃业务使用、未知持有者、验证失败或清理失败时保留卷并报告原因。
- 不自动删除 Pod、停止容器、终止进程，不执行强制或延迟卸载，不修改 Promtail 部署，不进行线上破坏性验证。

## 2. 已知背景与当前实现

用户报告的现场占用者为 monitoring/promtail-ftnz4，容器主进程为 /usr/bin/promtail。宿主机卸载后，该容器的挂载命名空间仍持有目标逻辑卷的文件系统，设备打开计数为 1。

本次 Pod 名、容器 ID、PID、命名空间 inode 和卷名只作为现场报告，不作为代码中的固定标识。最初报告末尾的删除命令曾截断卷名；用户后续现场验证明确了完整目标为 `/dev/vg_data1/lv_nb_57fc4e9250ee4cadb6f43dff96c48d54`，与挂载目录后缀一致。

### 2026-10-09 用户现场验证（已完成）

用户提供 worker-1-10 上的实际执行记录：

1. 执行 `sudo nsenter -t 2478731 -m umount /data02/nfs_lv_nb_57fc4e9250ee4cadb6f43dff96c48d54`，普通卸载成功，未使用 `umount -f` 或 `umount -l`。
2. `dmsetup info -c` 输出对应设备主次号 `253:0`、打开计数 `0`。
3. 执行 `sudo lvremove /dev/vg_data1/lv_nb_57fc4e9250ee4cadb6f43dff96c48d54`，确认交互提示后返回 `Logical volume "lv_nb_57fc4e9250ee4cadb6f43dff96c48d54" successfully removed.`。

结论：该现场案例已验证“目标命名空间内普通卸载 → 打开计数归零 → 删除逻辑卷”的恢复顺序可行，无需重启 Promtail。LVM 提示 active 是卷仍处于激活状态，不等同于文件系统仍被占用。

此证据由用户提供，不是助手执行或独立复现；它证明该现场案例的手工恢复成功，不证明 control_panel 自动修复已实现，也不替代其他命名空间根目录、传播属性、授权条件和竞态的测试。

当前实现位置：

- `backend/internal/storage/handlers.go`：检测宿主机挂载，执行 Pod 使用检查，卸载宿主机挂载，首次 lvremove 失败后调用命名空间清理并重试。
- `backend/internal/storage/commands.go`：`CleanupNamespaceMountsCmd` 扫描 `/proc/*/mountinfo`，使用宽泛字符串匹配，调用 `nsenter ... umount -f`，忽略卸载错误。
- `backend/internal/storage/handlers.go`：清理调用忽略执行错误和退出码，可能错误记录为成功。
- `backend/internal/k8s/pod_guard.go`：现有检查识别直接 NFS 与 PVC/PV 支持的 NFS 来源，不足以识别所有 hostPath 持有者；部分未解析引用被忽略。
- `backend/cmd/server/main.go`：Kubernetes 客户端缺失时允许注入空检查器；现有删除处理器会跳过检查。

2026-09-30 的设计要求仅诊断残留持有者、不强制卸载。此次确认允许有条件的普通卸载，替代旧文档中的“绝不自动清理”边界；旧文档中保留业务 Pod 阻止删除、查询失败停止等安全要求。

## 3. 非功能要求和显式假设

### 已确认约束

- 自动操作限于目标节点、目标逻辑卷和已核实的残留挂载。
- 查询失败、占用仍存在或清理失败时停止删除。
- 不强制卸载、不延迟卸载、不自动重启或删除 Pod。
- 不修改开发 SQLite 数据库，不执行现场手工命令。

### 用户已确认的默认值

- 使用显式工作负载许可名单决定自动清理资格，默认空名单。未配置时仍可诊断，不自动执行命名空间卸载。
- 名单按命名空间、DaemonSet 名称和容器名称精确配置；不以 Pod 名称前缀、进程名或标签单独授权。现场实际 DaemonSet/容器名尚未提供，部署时核对，不从 Pod 名猜测。
- 单次恢复阶段总预算暂定 60 秒，单次远程普通卸载最多 10 秒；均受任务剩余期限约束。
- 验证设备打开计数最多 3 次，间隔暂定 1 秒。计数非零时不重试删除。
- 命名空间清理最多一轮，lvremove 最多一次额外重试；无无限轮询或后台常驻扫描。
- 已核实 `internal/tasks/engine.go` 的 `slotFor` 将 storage/worker 任务统一串行到同一 worker ID；单后端进程内复用此互斥，不另加同作用域锁。此保证不覆盖同一物理节点被注册为多个 worker ID、多个后端进程或外部管理员/控制器操作。部署继续要求单进程/单副本，并避免节点重复注册。
- 不保证日志采集完全无影响。许可名单表示管理员同意回收该已停用卷的容器挂载，不表示容器绝不会访问目录。

性能与规模：正常成功回收不增加 `/proc` 全量扫描；恢复阶段对目标节点扫描进程信息，按挂载命名空间去重。节点实际进程规模未给出，以超时停止作为上限，不宣称固定延迟保证。

安全与隐私：远程操作沿用现有 SSH 权限边界；日志记录设备、挂载、命名空间及工作负载身份，不默认记录完整命令行、环境变量或凭据。

维护：由 control_panel 后端维护者管理代码与测试；部署管理员维护许可名单。配置语法和超时值必须校验，错误配置阻止启动或明确禁用恢复，不能静默扩大权限。

## 4. 方案比较与决策记录

| 决策 | 采用方式 | 替代方式 | 理由与状态 |
| --- | --- | --- | --- |
| 自动操作权限 | 已核实后的普通命名空间卸载 | 仅人工诊断；自动重启 Pod；强制卸载 | 用户已明确允许普通卸载，拒绝强制和重启 |
| 恢复触发时机 | 首次 lvremove 明确报文件系统占用之后 | 每次删除前都扫描并清理 | 用户要求继续细化推荐方式；改动集中，正常路径成本较低 |
| 清理资格 | 显式工作负载许可名单，默认空 | 进程名匹配；所有残留挂载均清理 | 用户已确认；“未发现 NFS Pod”不能证明 hostPath 持有者可清理 |
| 设备匹配 | mountinfo 第 3 字段精确比较主次设备号，并关联稳定逻辑卷身份 | grep 设备路径、卷名或主次号子串 | 防止相似卷名、字段误匹配和设备号复用 |
| 失败处理 | 保留卷，记录实际失败及部分清理状态 | 忽略退出码并记成功 | 已确认安全边界，不虚报结果 |
| 重试策略 | 一轮清理、一次删除重试 | 无限扫描、无限删除重试 | 有界执行，便于维护和诊断 |

## 5. 组件边界

### 存储任务编排

删除任务保留在 `internal/storage`，负责状态机、超时、任务记录和停止条件。通过窄接口依赖 Kubernetes 使用检查和工作负载授权查询，不让 storage 包依赖 API 包。

沿用 SSH Runner 接口。新增只读扫描、按授权目标清理、设备状态验证能力；以结构化结果传递设备身份、命名空间、进程身份、挂载 ID、挂载路径和传播属性，不依赖解析人类可读日志作授权判断。

### Kubernetes 检查和授权

在 `internal/k8s` 查询新鲜 Pod、PVC、PV 及相关 DaemonSet 对象。

- 业务 NFS 引用存在即阻止删除，包括 Pending 和 Terminating Pod。
- 缺失客户端、无法解析的潜在相关引用、列表或身份验证失败时停止删除。
- 已知目标导出路径时检查该路径及子路径；未知路径时采用原设计的保守 worker 范围判断。旧 exports/fstab/任务参数只作线索，不能独立证明当前卷绑定。
- 通过节点身份、Pod UID、容器运行时 ID、cgroup 证据关联实际命名空间；验证 DaemonSet ownerReference 的 UID 与新鲜 DaemonSet 对象一致。
- 容器须精确命中许可名单，且对应挂载证据与获准的父目录 hostPath 继承情形一致。直接业务卷引用仍是阻止条件，即使 Pod 同时命中名单。
- 共享挂载命名空间中的所有相关容器和持有者均需可识别、可授权；存在未知持有者时不清理。

运行时证据只读，不引入通过 crictl 自动停止或重建容器的能力。无法可靠获取/解析容器身份时降级为诊断，不猜测授权。

## 6. 回收状态机

1. 校验 worker、VG/LV 名称、受保护挂载点，读取并固定逻辑卷身份（例如 LV UUID）与当前主次设备号。
2. 解析宿主机 live mount 证据，进行新鲜业务 Pod 使用检查。Kubernetes 不可用时停止，不以开发模式为由允许破坏性删除。
3. 沿用撤销 NFS exports、普通卸载宿主机目标、清理 fstab、确认宿主机已卸载的流程。部分清理失败时记录状态并保留卷。
4. 在首次 lvremove 前再次检查业务 Pod，降低删除期间新建 Pod 的风险。
5. 首次删除成功则结束。只有明确的 LVM 文件系统占用错误进入恢复流程；SSH 传输错误、参数错误或其他 LVM 错误不触发清理。
6. 只读扫描所有目标设备的挂载命名空间，按 namespace inode 去重。精确解析 mountinfo 字段、分隔符及路径转义。
7. 获取每个持有者的容器/Pod 关联和授权结果；在任何命名空间卸载前完成全部候选检查。未授权、未知、工具缺失、权限不足或危险挂载结构时停止自动恢复。
8. 再次检查业务 Pod，并进入受限普通卸载阶段。每次操作前核对固定的设备与进程、命名空间、挂载身份。
9. 清理后重新扫描目标设备的残留挂载，并验证 dmsetup 打开计数。未能确定设备仍为同一 LV、计数读取失败、计数非零或仍有挂载时停止。
10. 重试前最后一次新鲜业务 Pod 检查，且重新核对 LV 身份。通过后只重试一次 lvremove。
11. 只有实际 lvremove 成功才记录整项回收成功；失败保存最新错误及此前恢复阶段的真实结果。

多次检查只能降低竞态，不能提供与 Kubernetes 新建 Pod、特权容器 remount 或外部 LVM 操作的原子互斥。最终内核/LVM 占用检查仍必需。本次不增加 Kubernetes admission/controller。

## 7. 普通卸载的安全要求

### 精确目标与路径上下文

- 只接受精确属于目标设备的 mountinfo 记录；名称与字符串子串不作依据。
- 对挂载路径的 mountinfo 转义进行标准解码，路径通过结构化输入或安全参数传递，不插入未经转义的 shell 片段。
- 必须使用目标进程的根目录/工作目录语境解析容器内挂载路径；仅切换 mount namespace 而继续使用宿主机根目录不足以保证目标正确。
- 不卸载目标命名空间根挂载，不触碰保护路径，不递归卸载父目录来间接清理目标。
- 使用 mount ID 与路径复核实际顶层挂载，防止堆叠挂载导致卸载错误层。

### 传播、子挂载与并发变化

- 扫描并验证 shared/master 等传播属性，确定卸载不会传播到未授权命名空间。无法证明传播影响受限时拒绝自动清理，不修改传播属性绕过判断。
- 同一设备存在多个合法挂载时按挂载树关系深层优先处理；挂载路径字典序不是挂载树深度的替代。
- 若目标下方有不属于该逻辑卷的子挂载或无法识别的层叠挂载，停止而不是卸载其他设备。
- 固定 mount namespace 引用并验证代表进程身份及根目录上下文，防止扫描与执行之间 PID 退出或复用；必须核实所选工具实现能提供这些保证。
- 固定命名空间引用本身可能延长其生命周期，恢复完成、失败、超时均应释放引用，避免制造新的残留占用。
- 代表进程消失后先重新扫描；只有确认候选挂载自然消失才能将其视为无需清理，不能泛化为忽略 /proc 错误。

### 工具与超时

- 检查所需工具、参数支持和权限；不以强制参数、忽略错误或自动停止容器作为兜底。
- 每个远程操作与整个恢复阶段均有执行期限。仅取消 SSH 连接不保证远程进程退出，远端必须有可验证的超时/终止与资源释放机制。
- 非零退出码、工具报错或状态验证失败记录为失败。即便卸载进程超时退出，也必须重新检查实际挂载状态，不能仅凭退出状态断言未发生变化。

## 8. 任务记录和失败语义

建议保留/增加可读步骤：`check_pod_usage`、`verify_pod_usage`、首次删除尝试、`scan_namespace_holders`、`authorize_namespace_cleanup`、`cleanup_namespace_mounts`、`verify_device_released`、最终删除重试。

已核对 Reporter：`Step` 创建 running 步骤，`Done` 独立完成步骤，任务 `Fail`/`Succeed` 首次调用即固定最终结果。实现时应立即完成首次失败的删除步骤，恢复成功前不调用任务级 `Fail`，最终重试创建独立步骤。任何新增步骤创建失败均须停止，不能像当前恢复调用一样忽略 `r.Step` 错误。

步骤名称与 Reporter 生命周期应在实现计划中核对，避免悬挂或重复结算的步骤。首次失败后恢复成功，应显示“首次占用，清理后重试成功”，不能覆盖首次结果造成不可追溯。

记录：设备/LV 身份、命名空间标识、经授权的工作负载身份、挂载路径、实际退出码、超时、验证结果和最终 LVM 错误。不保存完整进程命令行。

没有允许自动清理的候选、设备打开计数非零但没有发现挂载、或者存在未知占用时，输出只读诊断和人工处理建议，保留逻辑卷。Open Count 非零也可能来自非挂载持有者，不能继续盲目 namespace 卸载。

“未授权”“失败”“无需清理”“已完成部分卸载”应明确区分。命名空间清理失败后不再次尝试 lvremove。业务检查失败若发生在 exports/fstab 清理后，应报告已发生的部分变更，不声称节点完全未改变。

## 9. 测试与验收

采用失败测试先行，验证真实命令行为而不只检查命令字符串。

### 单元与流程测试

- 精确主次设备号匹配，不匹配相似卷名、子串和其他字段。
- namespace 去重、路径转义、挂载树顺序、共享/从属传播、层叠挂载和异设备子挂载。
- 许可名单为空、命中、未命中；伪造名称/标签、owner UID 不匹配、节点/容器 ID 不匹配、同 namespace 未授权持有者。
- PID 退出/复用、挂载变化、LV UUID/设备号变化、根目录上下文变化。
- 扫描失败、权限缺失、工具不支持、超时、状态读取失败均停止恢复。
- 卸载失败不记成功、不重试删除；部分卸载可真实报告。
- 清理后挂载消失且打开计数为 0，最终删除成功。
- 挂载已消失但打开计数仍非零、没有 mount holder、最终 lvremove 仍报占用。
- 业务 Pod 在清理前或重试前出现；Kubernetes 客户端为空、查询失败、引用无法解析时失败关闭。
- 目标导出路径未知时保守阻止潜在 worker NFS 使用；正常删除、多宿主机挂载、保护目录等既有行为不回归。
- 报占用错误识别覆盖 stdout/stderr 与实际 LVM 错误形式；传输失败不触发恢复。

### Linux 隔离验证

在专用 Linux 测试环境构造隔离 mount namespace 和临时测试设备，验证目标进程根目录、namespace 固定、路径解析及普通 umount 的行为。不得使用生产 VG/LV、生产目录或线上 Promtail Pod。

Windows 工作区无法独立证明 Linux 内核与 nsenter 行为。若隔离环境暂不可用，明确记录未验证项，不能以 mocked SSH 通过宣称生产问题已解决。

### 静态与回归验证

运行 `go test ./...`、`go vet ./...`、相关配置/部署验证和 `git diff --check`。禁止把开发数据库改动纳入本次提交或发布。

## 10. 发布与回退

配置与部署文档说明许可名单、超时和工具要求。默认空许可名单；管理员核对真实工作负载身份后显式启用。

Git 修改不等于部署生效，需要独立构建并发布后端镜像、更新运行中的部署。

已核对现有原生清单 `deploy/rbac.yaml` 与 Helm 模板 `charts/control-panel/templates/rbac.yaml`：均未授予 DaemonSet 读取权限。若按本设计核验 owner UID，实施时须为 `apps/daemonsets` 增加仅 `get` 的权限，并添加 RBAC 测试；无需授予 DaemonSet/Pod 的修改或删除权限。部署前检查该只读权限及目标节点工具兼容性。

回退方式为清空许可名单/禁用自动恢复，保留诊断和普通回收能力；不得恢复当前忽略清理失败和强制卸载的实现。已卸载的容器挂载不会由应用配置回退自动复原，需要由维护人员评估。

## 11. 独立复核与实施修正

用户已经确认详细设计、空许可名单、时间预算和保守拒绝风险，并授权实施。独立复核要求纳入以下修正：

- `storage_reclaim_nfs` 与 `storage_delete_lv` 共用安全删除流程；通过 provision task 回收时在 API 提交前确定真实 worker，执行前核对 task target，避免取得错误节点的串行锁。
- 首版只自动处理明确叶子挂载，拒绝子挂载、层叠挂载和未核实的传播风险。目标与父挂载均须验证，宿主机首次卸载前也不能跳过。
- 采用嵌入的可信宿主机 Python3 帮助程序，在进入目标 root/namespace 前加载 libc，直接调用 flags=0 的普通卸载系统调用，不执行容器里的工具、加载器或 helper。这是为正确处理 root/path 而增加的明确节点工具依赖。
- 同一次远端清理调用固定并复核 namespace/root FD，核对所有 namespace 成员的 PID/starttime/cgroup，确认终止并释放引用后，再独立复查设备打开计数。
- 仅支持独立普通 LV，禁止 snapshot origin、thin pool 等复杂/依赖对象；同时校验 LV basename 与稳定 UUID。
- 回收前检查所有 live aliases，识别祖先 NFS 导出、节点地址别名和直接 hostPath/PV 业务引用，无法排除潜在相关使用时停止。
- 远端清理前创建 `/run/control-panel-storage-recovery.uncertain`；超时或无法确认退出时保留，存储任务每条远端命令先检查该标记，防止后续任务与未知执行器交错。管理员只在核实执行器终止与挂载状态后解除。
- Linux 隔离验证是开启许可名单的部署前置条件；本机无 WSL 发行版时可交付默认关闭的代码及解析测试，但不能宣称新执行器已验证生产行为。

复杂传播图、通用挂载拓扑和额外运行时不纳入首版。生产 Git 推送不等于镜像、Chart OCI 发布或线上部署。详见 `control_panel/docs/nfs-namespace-recovery.md`。
