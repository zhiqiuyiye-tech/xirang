# NFS 虚拟盘残留挂载自动回收

## 行为

`storage_delete_lv` 和 `storage_reclaim_nfs` 共用删除流程。业务 Pod 仍引用卷，或者 Kubernetes 查询结果不确定时，保留逻辑卷。按手工流程先撤销导出、普通卸载宿主机，再在首次 `lvremove` **之前**扫描其他进程的挂载命名空间，核实残留持有者身份。只有显式许可的日志采集容器才允许进入其固定的 namespace/root 上下文普通卸载；设备身份不变、残留挂载消失、Open Count=0 并复查业务使用后，才删除逻辑卷。

前置检查通过后，若竞态导致首次 `lvremove` 又明确报文件系统占用，仍保留原来的受限清理和仅一次重试兜底；普通传输/参数错误不触发重试。清理失败不继续删除，不把“命令已提交”记录成实际成功。

不自动重启 Promtail，不删除 Pod，不终止业务进程，不使用强制或延迟卸载。任务日志保留首次删除失败和最终恢复结果，清理失败不会显示成功。

## 启用条件

自动清理默认关闭，许可名单为空。Git 推送、Chart 升级或镜像更新不会自动给所有容器授权。

1. 使用单个 control_panel 后端实例，避免同一节点登记为多个 worker；回收期间不并行手工修改 LVM。
2. 所有虚拟盘删除的目标 worker 安装 `python3`（3.7及以上）、GNU `timeout`（coreutils）、`lvm2`，并具备读取完整 `/proc`、进入 mount namespace、chroot 及普通卸载所需权限。新工具前置条件不由旧版“安装依赖”按钮自动保证。
3. 控制面服务账号需要现有 Pods/PVC/PV/Nodes 只读权限和新增的 `apps/daemonsets get`。无需增加 Pod 或 DaemonSet 删除/修改权限。
4. 先在独立 Linux 测试环境验证 namespace/root 和普通卸载行为；Windows Go/Python 解析测试不等于 Linux 内核验证。
5. 核对真实的命名空间、DaemonSet 名称和容器名称，再配置精确的 `namespace/daemonset/container`。例如 `monitoring/promtail/promtail` 仅为示例，不能从某次 `promtail-xxxxx` Pod 名或 PID 推断永久身份。

许可名单中的工作负载应是受信任的日志采集程序；限制该命名空间中创建或修改 Pod/DaemonSet 的权限。许可意味着管理员允许移除已停用卷在该容器中的残留挂载，不保证日志采集完全无影响。

## 配置

| 环境变量 | Helm values | 默认值 |
| --- | --- | --- |
| `SHARED_HOST_MAINTENANCE_ENABLED` | `config.sharedHostMaintenanceEnabled`（布尔值） | `false`，维护模式关闭 |
| `NAMESPACE_CLEANUP_ALLOWLIST` | `config.namespaceCleanupAllowlist`（字符串列表） | 空列表，关闭自动清理 |
| `NAMESPACE_CLEANUP_TIMEOUT` | `config.namespaceCleanupTimeout` | `60s` |
| `NAMESPACE_UNMOUNT_TIMEOUT` | `config.namespaceUnmountTimeout` | `10s` |

环境变量许可名单使用逗号分隔；不支持通配符。总恢复预算最多5分钟，单次卸载期限最多10秒，且单次期限不能超过总预算。配置错误阻止启动。

Helm 中可以配置 `config.namespaceCleanupAllowlist: ["monitoring/promtail/promtail"]`，替换为已经核对的实际名称。原生清单在 `deploy/deployment.yaml` 配置同名环境变量。清空名单并重启后端即可关闭自动恢复；已经完成的卸载不会因此自动恢复。

## 保守拒绝情形

首版只支持明确识别的独立普通 LV 与安全叶子挂载。未知持有者、未知导出路径、运行时身份不匹配、主机进程、复杂/层叠/子挂载、存在未核实的向外传播风险、保护目录、快照/薄池等复杂逻辑卷、缺少工具或权限，均停止自动操作并报告原因。

宿主机不向外传播的叶子挂载和残留命名空间清理沿用直接父挂载的局部传播检查。叶子本身的单个 `shared:N` 不表示卸载该叶子会向外传播：删除事件由直接父挂载决定。程序允许已授权的普通或共享叶子在真实私有父挂载或纯从属（HostToContainer）父挂载下普通卸载，因为从属父挂载仅接收宿主机事件，不会向 master 传播局部卸载；仍拒绝向外共享的直接父挂载、从属/多重叶子挂载元数据、未知父挂载、层叠与子挂载；resize 的原有保守身份检查不随之放宽。共享宿主机挂载另走受控路径，始终不会修改传播设置或递归卸载其他设备。执行器使用可信宿主机解释器和普通卸载系统调用，不执行容器提供的 `umount`、动态加载器或辅助程序。

## 共享宿主机挂载的受控回收

Linux/systemd 节点的根挂载常为 shared，直接挂载在其普通子目录下的 LV 也可能继承 shared。此状态不是磁盘损坏。共享回收仅支持一个宿主机 LV 叶子挂载；目标是根挂载、受保护路径、多个宿主机别名、层叠或子挂载时仍拒绝。

1. 删除专用只读检查区分私有路径与需要传播授权的路径；不会放宽 resize 和容器内直接卸载的私有限定。
2. 共享路径要求节点位于初始 user/mount namespace，具备宿主机 CAP_SYS_ADMIN，架构为 x86_64/aarch64，并支持 Linux 6.12 引入的 `NS_MNT_GET_INFO/NEXT/PREV` ioctl（或兼容回移）。单纯扫描 `/proc/*/mountinfo` 无法发现仅被文件描述符或 SCM_RIGHTS 消息队列引用的命名空间，因此没有内核枚举能力时明确拒绝，不静默降级。
3. 前后两次内核 namespace 清单、唯一 namespace ID 和挂载数量必须一致，且与进程/线程的完整 root/mount 视图吻合。没有可识别成员的命名空间、隐藏或不完整的 root 视图、读取权限不足、规模超限均停止。首版保守拒绝任何无法与进程视图对应的命名空间，即使尚未证明它持有目标设备。
4. 根据直接父挂载的 peer/slave 传播图和文件系统内挂载位置，核对可能被卸载的目标副本。异设备、异文件系统子根、层叠、子挂载或未知传播属性停止；不仅按目标的 shared 编号匹配。
5. 所有其他命名空间中的 LV 持有者（包括不接收传播的私有副本）都须经现有 `NAMESPACE_CLEANUP_ALLOWLIST` 精确授权。空名单或未知成员阻止共享回收；仅在完整清单证明不存在其他 LV 持有者时，可执行宿主机自身的普通卸载。
6. 移除 exports 前、普通卸载前分别复查完整证据摘要、授权和业务使用；远端受监督子进程再次核对内核清单、进程、挂载、设备身份及 mount ID，再执行 flags=0 的 `umount2`。共享权限只用于宿主机的受控卸载，不授予容器内共享挂载清理权限。
7. 卸载后重新扫描所有进程命名空间，并在最终释放验证中重新核对完整内核 namespace 清单和挂载数量。确有残留时只允许原有私有挂载清理，仍须单独重新授权；共享残留或未知占用保留卷。内核清单与进程视图一致、所有命名空间无目标挂载且 Open Count=0 后，才允许首次 lvremove，并在删除前再次验证。共享阶段总预算沿用 `NAMESPACE_CLEANUP_TIMEOUT`。
8. 实际卸载 helper 派发后的任何异常退出、超时、设备变化或后验失败，均保留不确定状态标记并隔离该 worker。卸载前已确认没有变更的证据拒绝可以清除标记。

传播范围证明依赖受控维护条件：外部管理员、特权容器、挂载控制器和 LVM 操作不能与回收并发修改相关状态。内核枚举、Kubernetes 查询及路径复核不是原子事务，应用内 worker 串行锁也不能约束这些外部操作者；不得把本实现宣称为能抵御任意并发特权 remount 的原子删除。必须在隔离 Linux 环境验收内核枚举、真实 peer/slave 卸载、忙挂载、状态变化和 helper 终止后再部署共享回收。旧内核或证据不全的节点在严格模式下继续保守拒绝；旧内核只有明确选择下述维护模式并满足其人工授权条件后，才可按较弱的进程可见保证回收，不能以修改整个 `/` 的传播属性绕过。

如果卷已经在宿主机卸载且无法证明当前导出路径，会采用保守业务检查，并拒绝不能授权的自动清理。历史任务参数和旧 fstab/exports 条目只作线索。

## Linux 5.10 的显式维护期回收

worker-3-10 已确认运行 `5.10.0-136.12.0.90.ctl3.aarch64`，`NS_MNT_GET_INFO/NEXT/PREV` 均返回 ENOTTY（errno=25）。该节点不能使用上述严格内核证明路径。维护模式沿用现有 Go/Python 执行器，明确只校验进程可见的挂载/传播范围，不把 `/proc` 清单宣称为完整内核命名空间清单。

维护模式必须同时满足两道授权：

- 服务端设置 `SHARED_HOST_MAINTENANCE_ENABLED=true`，或 Helm `config.sharedHostMaintenanceEnabled: true`。默认关闭，只接受 `true`/`false` 配置；开关开启本身不会把普通任务切换到维护模式。
- 每一项新提交的虚拟盘删除/NFS 回收任务单独勾选维护确认，或在对应 API 请求中显式发送 JSON 布尔值 `"maintenance_confirmed": true`。未勾选、未传参、传 `false` 均保持严格模式；字符串 `"true"`、数字和 null 在 API 层拒绝。该确认保存在本项任务参数和提交审计中，不从历史 provision 任务继承。

维护前，管理员必须先在隔离的 Linux 5.10 测试环境验证，再确认完整维护范围，包括不可见或仅被描述符/消息队列持有的命名空间，并协调相关调度器、挂载控制器、特权程序和外部 LVM 操作，确保整个任务（含排队等待）处于受控维护窗口。程序不会自动 cordon/drain 节点、删除 Pod、暂停控制器或终止进程，也不能替管理员自动证明这些条件。

两道授权通过后：

1. 扫描所有可读进程/线程的 namespace/root/mount 视图及可见 namespace FD 引用，复用同一传播图和文件系统坐标校验。可见的未知持有者、业务引用、无成员的可见 pin、不完整 root 视图、异设备接收者、子挂载和层叠挂载继续阻止操作。
2. 外部 LV 持有者仍须精确命中 `NAMESPACE_CLEANUP_ALLOWLIST`；维护确认不替代工作负载授权，不扩大容器内清理许可。残留容器挂载仍只能通过原来的私有传播清理路径处理。
3. 移除 exports 前和普通卸载前复查可见范围、进程身份、授权与业务使用；模式也绑定到快照摘要和本项任务上下文，不能将维护快照重放为严格证明。严格模式失败、包括 ENOTTY，绝不会自动降级到维护模式。
4. 宿主机只执行普通卸载，不改变根挂载或其他挂载的传播属性，不使用强制/延迟卸载。删除前仍要求可见挂载消失、稳定 LV 身份、设备 Open Count=0，并在 lvremove 前再查一次。
5. 任务日志明确记录管理员维护确认和“process-visible scope only, not complete kernel namespace proof”。实际卸载阶段异常、超时或后验失败仍保留隔离标记并停止后续操作。

管理员的逐任务确认承担不可完全枚举范围的维护授权；此模式的保证弱于严格内核枚举模式，不是无需人工协调的全自动安全回收。完成/失败后须确认执行器退出、任务和隔离状态已核实，才可恢复外部变化并关闭维护开关。开关在后端启动时加载，关闭后需要重启/更新后端；Linux 5.10 的真实内核卸载验收未完成前保持默认关闭。

## 执行状态不明

远端恢复执行器在改变挂载前创建 `/run/control-panel-storage-recovery.uncertain`。只有确认执行器及其子进程结束时才清除标记。超时、连接丢失或退出情况不明时保留标记，阻止该节点后续存储命令，避免与尚在运行的执行器交错。后端同时将该 worker 加入进程内隔离名单，覆盖尚未确认远端标记创建的连接失败情况；仅在维护人员核实远端执行器已退出、挂载状态一致后，才可解除标记并重启后端以清除本地隔离。

出现该标记时由维护人员先只读确认恢复执行器已经结束、挂载和设备身份状态，再决定是否移除标记并重试。不能为了继续删除而直接清除标记；无法终止的内核等待需要节点维护处理。此标记不替代对外部管理员和控制器操作的协调。
