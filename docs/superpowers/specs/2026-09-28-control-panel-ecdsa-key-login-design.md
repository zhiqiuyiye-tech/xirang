# 控制面板 ECDSA P-256 私钥文件登录设计

- 日期：2026-09-28
- 状态：待用户审阅

## 目标与范围

将控制面板现有管理员密码登录替换为 ECDSA P-256 挑战签名登录。系统保留一个 `admin` 账号；所有操作者共享同一份私钥文件，因此不增加多用户、角色或逐人身份追踪。现有初始化管理员密码只用于首次登记公钥，以及运维恢复后重新登记；公钥登记完成时，密码登录立即关闭。

部署环境只能使用 HTTP，且入口通过内网 IP 白名单限制。前端采用项目内固定版本的 JavaScript P-256 加密库，以便在非 localhost 的 HTTP 来源上生成密钥和签名。HTTP 不能提供页面完整性和传输机密性；该限制是已接受的部署约束，不应在文档或界面中表述成与 HTTPS 同等安全。

## 账号与密钥生命周期

### 首次登记

1. 新数据库仍由 `ADMIN_INIT_PASSWORD` 初始化唯一管理员的 bcrypt 密码哈希。已有数据库的当前管理员密码哈希保留。
2. 登录页请求公开的认证状态接口。若管理员公钥为空，显示“初始化登录密钥”流程。
3. 浏览器在本地生成 P-256 密钥对，将私钥编码成未加密的 PKCS#8 PEM 文件，并触发下载。界面要求操作者确认已保存文件后再继续。
4. 浏览器只向服务端提交公钥与当前管理员密码。服务端只在公钥尚未登记且密码校验成功时接受请求；验证公钥确为 P-256 后，以 `public_key_pem IS NULL` 条件原子写入，避免并发引导覆盖彼此的密钥，再递增 `auth_version`、记录审计事件并签发会话 Cookie。
5. 公钥存在后，密码不得用于建立任何会话。密码哈希保留在数据库中，仅当运维按恢复流程清除公钥并重置引导状态后才能再次使用。

### 日常登录

1. 登录页提供私钥文件选择器，不在浏览器持久存储私钥。
2. 浏览器解析 PKCS#8 PEM，向服务端申请一次性挑战。
3. 服务端生成 32 字节随机 nonce 和随机挑战 ID，均以无填充 base64url 编码返回；挑战 2 分钟后过期，并保存到 SQLite。
4. 浏览器对以下 UTF-8 消息计算 SHA-256 并使用 ECDSA P-256 签名。`<challenge_id>` 和 `<nonce>` 是接口返回的 base64url 字符串，不做二次解码或重编码：

   `xirang-control-panel-login-v1\n<challenge_id>\n<nonce>`

5. 浏览器将挑战 ID 与固定 64 字节 `r || s` 签名（base64url，无填充）提交给登录接口。服务端原子消费挑战，再用已登记公钥验证签名。成功后沿用现有 JWT、HttpOnly 会话 Cookie 和 CSRF Cookie 流程。
6. 挑战过期、已消费、签名不正确、密钥格式不正确等情况均拒绝登录；无效签名也会消费挑战，避免并发重试。

### 轮换与恢复

- 已登录操作者可以生成新密钥文件并提交新公钥。界面先下载文件，再确认提交；服务端更新公钥并递增 `auth_version`，令其他所有会话和旧私钥失效，再为当前操作者签发新版本会话。
- 所有人共用密钥，轮换后必须通过受控渠道重新分发新文件。文件副本可登录，系统不能区分具体操作者；审计事件均归属 `admin`。
- 若所有私钥副本均丢失，运维先停止服务并备份 SQLite 数据库，再将管理员 `public_key_pem` 设为 `NULL`、将 `password_hash` 设为 `__PENDING_INIT__` 并递增 `auth_version`，然后重启服务。启动逻辑会用 Kubernetes Secret 中的 `ADMIN_INIT_PASSWORD` 重新初始化哈希；操作者可再次执行首次登记。
- 私钥文件是未加密的登录凭据。必须通过受控渠道分发并限制文件副本；丢失或泄漏时轮换公钥。

## 后端与数据库

### 数据迁移

新增一次性迁移：

- 在 `admin` 表增加可空的 `public_key_pem` 字段；不新增用户或角色表。
- 新增 `auth_challenges` 表，字段包括挑战 ID、nonce、过期时间与消费时间，并为过期时间建立索引。
- 迁移时递增管理员 `auth_version`，使升级前通过密码登录签发的旧会话失效。
- 发起新挑战时清理过期记录；挑战保留在 SQLite，保证挑战消费逻辑可原子执行。当前 Helm 部署为单副本，数据库仍是现有持久化 SQLite。

### HTTP 接口

- `GET /api/v1/auth/status`：返回是否已登记登录公钥，不返回公钥或密码状态细节。
- `POST /api/v1/auth/bootstrap`：仅在尚无公钥时接受 `{password, public_key_pem}`；校验密码、公钥曲线与 PEM 格式，登记公钥并签发会话。
- `POST /api/v1/auth/challenge`：创建并返回 `{challenge_id, nonce, expires_at}`。
- `POST /api/v1/auth/login`：接受 `{challenge_id, signature}`；只执行挑战签名验证，不再接受密码登录。
- `PUT /api/v1/auth/key`：需要现有认证与 CSRF 校验，接受新公钥并轮换密钥。
- `PUT /api/v1/auth/password` 及密码修改 UI 移除；替换为密钥轮换。
- 认证成功后继续设置当前会话和 CSRF Cookie；采用现有 `auth_version` 机制撤销旧会话。

### 安全与错误处理

- nonce 由 Go `crypto/rand` 生成；挑战 ID 不可预测且唯一，挑战只能消费一次。
- 服务端使用 `x509.ParsePKIXPublicKey`/PEM 解析并强制要求 `*ecdsa.PublicKey` 和 P-256 曲线；签名长度必须为 64 字节，再拆分 `r`、`s` 使用标准库验证。
- 挑战和登录失败按客户端 IP 复用现有登录限流；失败响应使用通用认证错误，审计记录成功、失败、限流、初始化和轮换事件，不记录密码、私钥、nonce 或签名。
- 登录继续使用 HttpOnly Cookie、CSRF 双提交校验和现有 JWT 发行方/受众校验。HTTP 环境保持 `COOKIE_SECURE=false`，仅供受信任内网白名单入口使用。

## 前端

- 将密码登录表单替换为私钥文件选择器；首次未登记时显示密码引导表单。
- 私钥生成、PEM 编码/解析、P-256 签名全部在浏览器完成。服务端只接收公钥、引导密码或签名，不接收私钥内容。
- 当前项目没有前端构建步骤；采用固定版本并随静态资源发布的 P-256 库，不从 CDN 动态加载，提交对应许可证和版本信息。实现时用标准 Go 生成的密钥与签名向量验证前后端互通。
- 设置区将“修改密码”替换为“轮换登录密钥”，清理过时的密码登录和密码修改提示。
- 对下载失败、浏览器不支持所需随机数 API、无效/错误曲线 PEM、网络错误和服务器返回的限流状态提供明确提示；私钥文件不放入 URL、localStorage 或 IndexedDB。

## HTTP 风险说明

随机挑战能阻止已消费 nonce 的签名被简单重放，但不能建立 HTTP 页面来源的真实性，也不能阻止主动中间人替换 JavaScript、读取私钥文件、窃取初始化密码或会话 Cookie。IP 白名单和内网隔离用于缩小可访问范围，不等同于 TLS。部署文档和登录页应明确此限制，并建议仅通过受控内网访问。

## 验证标准

- 单元测试覆盖 P-256 有效签名、错误签名、无效长度、非 P-256 公钥、错误 PEM、挑战过期、挑战重复消费及并发重复提交；并发首次登记只能成功一次。
- API 测试覆盖旧数据库迁移、首次密码引导只成功一次、登记后密码不能登录、有效签名登录与 Cookie 属性、轮换后旧会话失效、错误尝试限流、审计日志不泄漏凭据。
- 前端验证生成的 PEM 可被解析、重新导入的私钥能完成签名；与 Go 端共享签名向量。手工验证 HTTP 内网部署的首次登记、文件下载、退出/登录、轮换和离线恢复流程。
- 在 `control_panel/backend` 目录运行 `go test ./...`，并按仓库现有规则验证静态 JavaScript 与部署模板。
- 更新 `control_panel/deploy/README.md` 和 `control_panel/charts/control-panel/README.md`：说明首次初始化、私钥安全分发/备份、共享密钥带来的不可追责性、轮换与离线恢复，以及 HTTP 的明确风险。

## 不在范围内

- 多用户、角色、用户管理或个人级审计归因。
- WebAuthn/FIDO2、硬件安全密钥、密码保护的私钥文件、私钥云同步。
- 为 HTTP 增加自定义加密传输协议，或声称通过 ECDSA 挑战消除了 HTTP 中间人风险。
